# Zesty Restock Bot

Набор Telegram‑ботов для управления **отельными минибарами**: заселение/выселение гостей на ресепшене, расчёт списаний по минибару, контроль остатка и подтверждение пополнения.

Проект **не хранит состояние в памяти**: вся логика опирается на PostgreSQL (таблицы “bot2_*” и `guest_sessions`). Боты можно запускать в нескольких процессах/инстансах (с учётом ограничений polling).

---

## Что внутри

### 1) Reception Bot (ресепшн)
- free/occupied список комнат (свободно/занято)
- **Check‑in**: открыть гостевую сессию (`guest_sessions`) и привязать её к комнате
- **Check‑out**: закрыть сессию и сформировать чек по списаниям минибара за период
- **Transfer**: переселение гостя в другую комнату (цепочка `transfer_id`)

CLI‑команда: `reception-bot`

### 2) Restock Bot (хаускипинг)
- просмотр **текущего запаса** (по последнему snapshot‑транзакции)
- расчёт **недостающего по планограмме**
- подтверждение пополнения (помечает последнюю транзакцию как `event_type='restock'`)

CLI‑команда: `restock-bot`

## Быстрый старт

### Требования
- Python **3.13+**
- Poetry **2.x**
- PostgreSQL с уже существующей схемой (см. раздел **Database**)
- 2 Telegram Bot токена (для ресепшена и для пополнения)

### Установка

```bash
poetry install
```

### Конфигурация

1) Скопируйте пример окружения:

```bash
cp .env.example .env
```

2) Заполните переменные в `.env`:

- `DB_URL` — строка подключения к Postgres
- `TZ` — таймзона для отображения/отчётов (по умолчанию `UTC`)
- `RECEPTION_BOT_TOKEN` — токен бота ресепшена
- `RESTOCK_BOT_TOKEN` — токен бота пополнения

Пример (без реальных секретов):

```dotenv
DB_URL=postgresql://user:password@db-host:5432/dbname
TZ=UTC
RECEPTION_BOT_TOKEN=123456:REPLACE_ME
RESTOCK_BOT_TOKEN=123456:REPLACE_ME
```

### Запуск

**Ресепшн‑бот**:

```bash
poetry run reception-bot
```

**Ресток‑бот**:

```bash
poetry run restock-bot
```

## Database

Проект рассчитан на работу с уже существующей БД (часть более крупной системы), и использует таблицы:

- `bot2_hotel_rooms` — комнаты
  - ожидаемые поля: `id`, `room_num`, `category`, `id_hotel`, `guest_id`, `id_minibar`
- `guest_sessions` — сессии гостя
  - `id`, `room_id`, `check_in`, `check_out`, `transfer_id`
- `bot2_minibar_transactions` — транзакции‑снапшоты распознавания минибара
  - `id`, `id_minibar`, `transaction_timestamp`, `event_type`
- `bot2_minibar_transactions_details` — состав снапшота (1 строка = 1 единица товара)
  - `id_transaction`, `id_product`
- `bot2_products` — справочник товаров
  - `id`, `name`, `price`
- `bot2_planogram` — планограмма по категориям комнат
  - `room_category_id`, `id_product`, `planned_quantity`

### Как считается списание (логика чека)

Данные минибара приходят как **снапшоты**:
- каждая запись в `bot2_minibar_transactions` — это “состояние минибара” в момент времени
- детали (`bot2_minibar_transactions_details`) содержат фактический список товаров (повторы = количество)

Списание считается как **уменьшение количества** товара между соседними снапшотами.
Транзакция с `event_type='restock'` трактуется как **граница сброса** (после пополнения базовая точка отсчёта меняется).

## Структура проекта

```
src/restock_bot/
  bots/
    reception/   # UI и хендлеры ресепшн‑бота
    restock/     # UI и хендлеры ресток‑бота
  repositories/  # доступ к таблицам Postgres (asyncpg)
  services/      # доменная логика (check-in/out, restock, расчёт чека)
  common/        # DTO и доменные ошибки
  config.py      # pydantic-settings (.env)
  db.py          # пул подключений
```

## Деплой

Проект использует polling (aiogram). Для PaaS (Railway/Render/Heroku‑like) удобно заводить **два процесса**.

Пример `Procfile`:

```procfile
reception: poetry run reception-bot
restock: poetry run restock-bot
```

Окружение (`DB_URL`, токены ботов) задавайте через переменные окружения платформы.
